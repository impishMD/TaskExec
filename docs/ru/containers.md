# Контейнеры и раннеры

[English](../en/containers.md) | **Русский**

## Локальная сборка

Соберите и запустите TaskExec из исходников:

```sh
docker compose -f compose.yaml -f compose.dev.yaml up -d --build
```

Будет использован `taskexec:dev`. При переходе с JEH сначала [перенесите данные](migration.md).

## Имена релизных образов

| Роль | Версия | Стабильный тег |
| --- | --- | --- |
| Сервер | `v<version>` | `latest` |
| Раннер | `v<version>-runner` | `latest-runner` |
| Среда задачи | `v<version>-job` | `latest-job` |
| Вспомогательный образ | `v<version>-helper` | `latest-helper` |

Процесс выпуска публикует образы в `impishmd/taskexec` и `ghcr.io/impishmd/taskexec` для Linux amd64/arm64.
Сервер и раннер работают с UID 1001; подключённые каталоги должны быть доступны на запись.

Для опубликованного выпуска используйте [compose.yaml](../../compose.yaml) и [.env.example](../../.env.example),
указав опубликованную версию в `TASKEXEC_VERSION`. Для локальной сборки
добавляйте `compose.dev.yaml`, как в команде выше.
Тома `/etc/taskexec` и `/var/lib/taskexec` содержат конфигурацию и базу; при обновлении сохраняйте их.
Переменные администратора создают пользователя при первом запуске. Для смены пароля
существующего пользователя используйте `taskexec user change-by-login`.
PostgreSQL/MySQL настраиваются через `TASKEXEC_DB_DIALECT`, `TASKEXEC_DB_HOST`, `TASKEXEC_DB_USER`,
`TASKEXEC_DB_PASS` и `TASKEXEC_DB`. Для секретов доступны, например, `TASKEXEC_DB_PASS_FILE`
и `TASKEXEC_ADMIN_PASSWORD_FILE`.

## Удалённый раннер

Используйте опубликованный образ исполнителя той же версии, что и сервер, либо соберите
его командой `docker build --target runner -t taskexec:runner-dev .` и укажите этот образ ниже.
Включите **Управление (шестерёнка) → Общие настройки → Использовать удалённых
исполнителей по умолчанию** (или укажите тег исполнителя в шаблоне/инвентаре)
и создайте токен регистрации в интерфейсе администратора:

```sh
docker run -d --name taskexec-runner --restart unless-stopped \
  -e TASKEXEC_WEB_ROOT=https://taskexec.example.com \
  -e TASKEXEC_RUNNER_REGISTRATION_TOKEN="$RUNNER_REGISTRATION_TOKEN" \
  -v taskexec-runner-data:/var/lib/taskexec \
  impishmd/taskexec:latest-runner
```

Том исполнителя хранит его зарегистрированный токен. Для задач доступны локальное
выполнение и Docker-исполнитель.


## Docker-исполнитель задач

Удалённый исполнитель с `runner.executor.type = docker` запускает отдельный временный
Linux-контейнер на каждую задачу. Внутри используется основная логика TaskExec: клонирование
Git, инвентарь, ключи SSH и привязки хостов, пароли Ansible Vault, переменные, логи, данные
коммита, сводки Ansible и подтверждение Terraform. Автоматического перехода к запуску
на хосте нет.

Сборка образа задач из текущего кода:

```sh
docker build --target job -t taskexec:job-dev .
```

Образы сервера и исполнителя из того же кода тоже содержат рабочий процесс: для локальной
разработки можно использовать `taskexec:dev`. Старые job-образы, содержащие только
инструменты запуска, несовместимы. Собственный образ должен содержать
`/usr/local/bin/taskexec` с командой `task-worker` и необходимые инструменты. Создавайте
его на основе job-образа той же версии TaskExec. Пути к программам и политика SSH берутся
из образа задачи, а не из конфигурации хоста исполнителя.

Создайте активного исполнителя в **Проект → Исполнители**, назначьте ему тег, например
`docker`, и зарегистрируйте его либо используйте уже выданный зарегистрированный токен:

```sh
TASKEXEC_WEB_ROOT=http://localhost:3000 \
TASKEXEC_RUNNER_TOKEN_FILE=/path/to/runner-token \
TASKEXEC_RUNNER_EXECUTOR_TYPE=docker \
TASKEXEC_RUNNER_DOCKER_IMAGE=taskexec:job-dev \
TASKEXEC_RUNNER_DOCKER_PULL_POLICY=never \
taskexec runner start --no-config
```

Укажите такой же тег в шаблоне. Пустое поле **Образ контейнера исполнителя** использует
образ из настроек исполнителя; заполненное переопределяет его для шаблона. Локальный
исполнитель отклоняет шаблон с явно указанным образом контейнера.

Для Docker Desktop задайте `TASKEXEC_RUNNER_DOCKER_HOST` равным результату
`docker context inspect --format '{{.Endpoints.docker.Host}}'`. SDK читает `DOCKER_HOST`,
`DOCKER_TLS_VERIFY` и `DOCKER_CERT_PATH`, но не контексты Docker CLI. Явные настройки
хоста и сертификатов TaskExec имеют приоритет над соответствующими переменными SDK.

Исполнителю в контейнере нужен доступ к Docker daemon, например сокет и права на него.
Этот доступ получает только сам исполнитель: контейнерам задач не передаются сокет Docker,
каталоги хоста, база сервера или регистрационный токен. Пользователь берётся из образа;
привилегированный режим по умолчанию выключен. Доступ к daemon даёт управление его
контейнерами, поэтому хост исполнителя должен находиться под контролем доверенных администраторов.

Настраиваются сеть, ограничения CPU/памяти, TLS и политика загрузки образов: `always`,
`if-not-present` (по умолчанию), `never`. Для заранее загруженных приватных образов задайте
`never`: интеграция с авторизацией реестров и credential helpers пока не реализована.
Сеть контейнера должна иметь доступ к Git, целевым хостам и внешнему хранилищу состояния.
`localhost` внутри задачи — её собственный контейнер. Локальные репозитории должны быть
добавлены в образ: каталоги хоста автоматически не подключаются.

Данные задачи передаются через входной поток Docker. Секреты не попадают в переменные
окружения метаданных контейнера и аргументы запуска. Файлы ключей создаются внутри
временного контейнера. Из окружения исполнителя передаются только явно разрешённые
переменные и `env_vars`, вместе с переменными проекта и задачи. Образ задачи должен быть
доверенным: он получает доступ к её секретам.

Остановка отменяет подготовку/загрузку образа либо завершает контейнер. Разрыв соединения
с исполнителем также останавливает рабочий процесс. После успеха, ошибки и отмены
контейнер и анонимные тома удаляются. Постоянного рабочего каталога, кеша и экспорта
артефактов нет. **Для сохранения состояния Terraform/OpenTofu настройте remote backend**,
например [HTTP backend TaskExec](terraform-state.md).

### Проверка исполнителя

Проверки создают собственные контейнеры с тестовыми данными, без базы приложения:

```sh
docker build --target job -t taskexec:job-dev .
docker build --build-arg TASKEXEC_TEST_BASE=taskexec:job-dev \
  -t taskexec:docker-fixture services/tasks/docker/testdata
TASKEXEC_DOCKER_TEST_IMAGE=taskexec:docker-fixture \
  go test -race -timeout 4m ./services/tasks/docker
```

При необходимости задайте `DOCKER_HOST`, как описано выше. Проверяются Git, скрипты,
Ansible, подтверждение и отклонение Terraform, ошибки, отмена, параллельные задачи,
переопределение образа, лимиты ресурсов, отсутствие секретов в метаданных и очистка.
