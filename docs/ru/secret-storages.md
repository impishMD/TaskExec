# HashiCorp Vault

[English](../en/secret-storages.md)

TaskExec поддерживает HashiCorp Vault KV v1/v2.
Откройте **Проект → Хранилище ключей → Хранилища** и создайте подключение **HashiCorp Vault**.

## Подключение

- **URL сервера** — адрес, доступный серверу TaskExec, например `https://vault.example.com`.
  Сервер получает секреты перед передачей задачи локальному или удалённому исполнителю.
- **Путь хранилища KV** — точка монтирования KV-хранилища (mount), по умолчанию `secret`.
  Здесь указывается только путь самого хранилища, а путь конкретного секрета задаётся отдельно.
  Не вставляйте полный API-путь, `/v1`, служебные сегменты `/data` или `/metadata`.
- **Версия KV** — версия, настроенная для этой точки монтирования. По умолчанию **2**;
  версия не подбирается автоматически после ошибок подключения.
- **Пространство имён** — необязательно; используется, если его поддерживает ваш Vault.
- **Только чтение** — включено по умолчанию. Можно читать секреты,
  но нельзя изменять или удалять значения в удалённом хранилище через это подключение.

Сертификаты TLS всегда проверяются. В блоке **Расширенные** можно указать свой сертификат CA
в формате PEM либо установить его в доверенные сертификаты сервера. Перенаправления HTTP отклоняются, чтобы токен не уходил
на другой адрес. Ошибки подключения, отсутствие поля, некорректный ответ или отказ в доступе
прерывают операцию; пустое значение или локальный секрет вместо ошибки не подставляются.

Токену нужно право `read` на выбранные пути. Для автодополнения путей также нужно `list`:
в KV v2 — на `<mount>/metadata/...`, в KV v1 — на `<mount>/...`.
Для записи нужны `create`, `update` и `delete` на пути данных.
KV v2 использует проверку версии CAS, чтобы обнаруживать одновременные изменения.

## Пример: секрет `proxmox` в хранилище `secret`

Если в интерфейсе Vault открыто **Secrets → secret → proxmox → Paths** и указаны:

```text
API path: /v1/secret/data/proxmox
CLI path: -mount="secret" "proxmox"
```

заполните подключение TaskExec так:

| Поле в TaskExec | Значение | Что означает |
| --- | --- | --- |
| URL сервера | `https://vault.example.com` | Адрес вашего сервера Vault; замените домен своим |
| Путь хранилища KV | `secret` | Значение `-mount` из CLI path |
| Версия KV | `2` | В данном примере используется KV v2 |

**`/v1/secret/data/proxmox` в поле «Путь хранилища KV» — неверно.** Для этого примера
`secret/proxmox` и `secret/data` также неверны. Подключение описывает всё KV-хранилище `secret`;
нужный документ `proxmox` выбирается при настройке ключа.
Путь монтирования бывает вложенным: если CLI path содержит `-mount="team/kv"`, укажите
`team/kv` целиком. Его не следует определять только по первому сегменту API-пути.

TaskExec сам формирует запрос чтения KV v2:

```text
URL сервера                  + /v1/ + mount  + /data/ + путь секрета
https://vault.example.com     + /v1/ + secret + /data/ + proxmox
= https://vault.example.com/v1/secret/data/proxmox
```

Это соответствует [API чтения KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2#read-secret-version).
В KV v1 сегмента `/data/` нет: при тех же mount и пути запрос будет `/v1/secret/proxmox`.
**Версия KV** — версия движка хранилища, а не номер версии значения на вкладке **Version History**.

### Добавить ключ

1. Сохраните подключение; для чтения существующего секрета оставьте **Только чтение** включённым.
2. Откройте **Хранилище ключей → Ключи → Новый ключ** и задайте имя, например `test`.
3. Выберите источник **Хранилище** и созданное подключение.
4. В поле **Путь к секрету** укажите `proxmox`, без `secret/`, `/v1/`, `/data/` и `#поле`.
5. Выберите **Тип → Строка** и выберите `dns_server` в автоматически загруженном списке
   **Поле секрета**. Получится `test → документ proxmox → поле dns_server`.
   Для всего документа выберите тип **Набор переменных** — сопоставления не нужны.

Форма сохраняет только ссылку и сопоставления. Она не меняет значения в Vault, в том числе
при отключённом **Только чтение**. Для SSH и логина с паролем выбираются поля документа,
а не вводятся сами реквизиты. Тип, путь и сопоставления можно менять без **Переопределить**.
Поля загружаются автоматически при выборе или изменении пути и при открытии сохранённого ключа.
При ручном вводе запрос отправляется после короткой паузы; для каталогов с `/` поля не запрашиваются.
При недоступности Vault сохранённые сопоставления остаются видны и доступны для редактирования.

Старый формат `proxmox#dns_server` не поддерживается и автоматически не преобразуется.
Для такого ключа укажите отдельно путь `proxmox` и сопоставление `dns_server`.

Кнопка **Проверить вход** проверяет авторизацию, но не существование `secret/proxmox`
и не права чтения этого документа. Проверка входа может пройти даже при неверно заданном
пути хранилища; доступ к документу проверяется при чтении ключа.

## Аутентификация

Выберите способ входа в форме подключения — ниже появятся соответствующие поля.
Способ входа, роли и политики нужно предварительно настроить на сервере Vault.
**Путь аутентификации** — часть после `auth/`, например `approle` или `services/approle`.
Он не связан с **путём хранилища KV** (`secret` по умолчанию).

| Способ | Поля |
| --- | --- |
| Токен | Готовый токен Vault |
| AppRole | Role ID и Secret ID; путь аутентификации, по умолчанию `approle` |
| Kubernetes | Роль Vault и JWT сервисной учётной записи; путь по умолчанию `kubernetes` |
| JWT | Роль Vault и JWT; путь по умолчанию `jwt` |
| Сертификат | Клиентский сертификат PEM и закрытый ключ PEM без парольной защиты; имя роли необязательно; путь по умолчанию `cert`; требуется HTTPS |

У каждого реквизита свой источник: **БД**, **переменная окружения** или **файл**.
Значения БД и ссылки на источники хранятся вместе в зашифрованном ключе доступа. Сохраняйте
ключи шифрования вместе с резервной копией БД. Сохранённые значения скрыты. Пустое поле
сохраняет текущее значение только при том же способе входа и источнике. Для смены источника
нужно новое значение или ссылка; для смены способа входа — соответствующие ему реквизиты.

Файлы и переменные окружения читаются на **сервере TaskExec**, в том числе для удалённых
исполнителей. Путь файла должен быть абсолютным и находиться внутри `TASKEXEC_SECRETS_PATH`
(либо `dirs.secrets`). Для Kubernetes смонтируйте projected service account token в этот каталог
и укажите путь к нему. Стандартный путь Service Account вне каталога не разрешается автоматически.
Роль Kubernetes в Vault должна соответствовать сервисной учётной записи, namespace и audience.
Источник JWT должен предоставлять актуальный токен для нужной роли и audience. TaskExec сам
не запрашивает JWT у провайдера идентификации и не выполняет браузерный вход OIDC.

Полученные токены Vault хранятся в памяти сервера отдельно для каждого подключения и набора
реквизитов. Одновременные операции используют один вход. При обращениях возобновляемый токен
продлевается после двух третей срока действия; по истечении срока выполняется новый вход.
В периоды простоя фонового продления нет. Перезапуск TaskExec очищает кэш. Источники перечитываются
при подготовке каждой операции, поэтому смена файла или окружения меняет сессию.
Отказ в доступе к KV не вызывает повторных попыток входа.

Secret ID в AppRole может иметь срок действия и ограничение числа использований. Его замену
нужно организовать отдельно: TaskExec не создаёт Secret ID. **Проверка входа** может расходовать
использование Secret ID, особенно для нового несохранённого подключения. Для повторного входа
после перезапуска одноразовый Secret ID нужно заменить. Настройку **Эта AppRole не требует
Secret ID** включайте только для роли с `bind_secret_id=false` на стороне Vault.

**Проверить вход** проверяет черновик без сохранения и записи секретов. Для готового токена
используется `auth/token/lookup-self`, на который нужно право доступа. Для остальных способов
проверяется вход. Успех не гарантирует права чтения, просмотра списка или записи всех секретов.

## Ключи и значения

Путь всегда указывает на документ относительно точки монтирования KV. Поля выбираются
отдельно из актуального списка, полученного из Vault. В БД сохраняются только путь и имена
полей. Все поля одного ключа читаются из одной версии документа.

| Тип ключа | Обязательное сопоставление | Необязательные сопоставления | Результат |
| --- | --- | --- | --- |
| Набор переменных | Нет | Нет | Весь документ как объект, включая вложенные значения |
| Строка | Поле секрета | Нет | Значение выбранного поля; числа и bool преобразуются в строку |
| Логин с паролем | Пароль | Имя пользователя | Реквизиты для тех же подключений, что и локальный ключ |
| SSH-ключ | Закрытый ключ | Имя пользователя, парольная фраза | SSH-реквизиты для репозитория, инвентаря или настройки хоста |

Например, для документа `accounts/deploy` с полями `user` и `pwd` выберите:
**Имя пользователя → user**, **Пароль → pwd**. Для SSH поля могут называться `pem`,
`user` и `phrase`: сопоставьте их с закрытым ключом, именем пользователя и парольной фразой.
Необязательное поле можно не выбирать — оно останется пустым, как у локального ключа.
Выбранное поле должно существовать; поля реквизитов должны быть строками, обязательные
реквизиты — непустыми. Поле типа «Строка» не может содержать объект, массив или null.

### Использование в задачах через группы переменных

1. Создайте ключ `blabla`: источник **Хранилище**, путь `proxmox`, тип **Набор переменных**.
2. Откройте группу переменных, вкладку **Ключи**, нажмите **Добавить ключ** и выберите `blabla`.
3. Укажите имя переменной (по умолчанию имя ключа), цель передачи и **Значение целиком**
   либо конкретное поле. Форма показывает актуальное значение и время чтения. Кнопка
   **Обновить значение** читает источник заново. Значения не записываются в JSON группы
   и не сохраняются в браузере; сохраняются ID ключа, имя переменной, цель и имя поля.
4. Подключите группу к шаблону задачи.

Если в `proxmox` лежит `{"dns_server":"192.0.2.53","enabled":true}`, то для целого набора
в Ansible доступны `{{ blabla.dns_server }}` и `{{ blabla.enabled }}`. Список здесь означает
набор именованных переменных — объект, а не массив. Для полей с дефисами или именами методов
словаря, например `items`, используйте `{{ blabla['items'] }}`.

Если в привязке выбрать поле `dns_server` и имя переменной `dns`, получится `{{ dns }}`.
Для ключа типа **Строка** передаётся его значение целиком: при имени `blabla` — `{{ blabla }}`.
Вложенный объект или массив, выбранный из набора, сохраняет свой тип.

Если выбран набор и **Значение целиком**, TaskExec создаёт основную ENV с JSON объекта
и отдельную ENV для каждого поля первого уровня. Например, для имени `test` и секрета
`{"username":"demo","password":"example","options":{"enabled":true}}`:

| ENV | Содержимое |
| --- | --- |
| `$test` | Весь объект в виде JSON; например, `printf '%s' "$test" \| jq -r .username` |
| `$test_username` | Строковое значение `username` |
| `$test_password` | Строковое значение `password` |
| `$test_options` | JSON объекта `options` |

Префикс и регистр сохраняются: имя формируется как `ПРЕФИКС_ПОЛЕ`. Вложенные поля
не разворачиваются рекурсивно. При выборе отдельного поля создаётся только основная ENV.
В предпросмотре ENV и списке выбора полей показываются только имена, без содержимого.
Сформированные имена должны соответствовать `[A-Za-z_][A-Za-z0-9_]*` и быть не длиннее
255 символов. Поле с неподходящим именем можно привязать отдельно под допустимым именем.
Конфликт с другой переменной внутри группы прерывает подготовку задачи без частичного
добавления ENV. Новые значения и состав полей перечитываются при каждом запуске.

Цель **Переменные окружения** передаёт строку как есть, а объекты, массивы, числа, bool и null —
как JSON в переменную окружения. В Ansible её читают через `lookup('env', 'NAME')`;
для объекта добавьте `from_json`. В shell переменная доступна как `$NAME`.
Цель дополнительных переменных передаётся Ansible через JSON `--extra-vars`, Terraform/OpenTofu
через `-var`, скриптам — как аргументы `name=value` (составные значения в JSON).

Один ключ можно использовать под несколькими именами и выбирать разные поля набора.
Имена должны соответствовать `[A-Za-z_][A-Za-z0-9_]*`. Одинаковые имена для одной цели внутри
группы запрещены, включая обычные и секретные переменные. При нескольких группах значения
ключей с одинаковыми именами и целью берутся из последней группы. Ключи SSH и логин/пароль
не экспортируются в переменные: они выбираются как реквизиты соответствующего ресурса.
Удаление используемого ключа и несовместимая смена его типа запрещены.

Предпросмотр доступен пользователям с правом управления ресурсами проекта. Само сохранение
ссылки не требует чтения Vault. При запуске значения читаются заново: ротация не требует
пересохранения группы. Отсутствие документа/выбранного поля или ошибка доступа останавливают
подготовку задачи; устаревшее значение не подставляется. Для задач на удалённом исполнителе
значения читает сервер при подготовке и передаёт исполнителю по его рабочему каналу.
Не выводите секреты в задаче без необходимости; для чувствительных шагов Ansible используйте
`no_log: true` — произвольный вывод самого плейбука попадает в журнал задачи.

Удаление ключа через интерфейс удаляет только ссылку из TaskExec, включая подключения
с разрешённой записью. Значение в Vault сохраняется.

Для интеграций API сохраняет отдельный режим записи: без `reference_only` можно записывать
значения в хранилище с отключённым **Только чтение**; при обновлении требуется `override_secret: true`.
Пустой путь при таком создании автоматически заменяется на `taskexec/<случайный-id>`.
Запись сохраняет посторонние поля документа. API-удаление без `reference_only=true` для обычного
ключа из хранилища с записью удаляет удалённое поле или документ. Для KV v2 удаляется текущая
версия с сохранением истории. Для синхронизированных ключей и подключений только для чтения
удаляется лишь ссылка. Удалённый путь KV v2 с историей нужно восстановить либо заменить новым.

Удаление подключения не удаляет секреты на сервере и запрещено, пока на него ссылаются
ключи или группы переменных.

## Сопоставление значений в группе переменных

Вверху формы группы добавьте **Ключи доступа** кнопкой **+**. Для каждого выберите ключ
типа **Строка** или **Набор переменных** и уникальный префикс, например `test`.
Один ключ можно подключить под разными префиксами. Префикс начинается с латинской буквы
или `_` и содержит только латинские буквы, цифры и `_`; регистр учитывается.
Сам по себе префикс не создаёт переменную задачи.

На вкладках **Переменные** и **Секреты** укажите нужное имя переменной, а в значении
вставьте ссылку через кнопку `{}` или начните вводить `{{`. Подсказки загружают актуальные
имена полей без содержимого секретов. Кнопка обновления возле ключа перечитывает поля.

| Имя | Значение в форме | Результат |
| --- | --- | --- |
| `dns_server` | `{{ test.dns_server }}` | Значение поля выбранного ключа |
| `DATABASE_PASSWORD` | `{{ test.password }}` | Пароль под произвольным именем ENV |
| `DATABASE_URL` | `postgres://{{ test.username }}:{{ test.password }}@db` | Составная строка |
| `settings` | `{{ test }}` | Весь набор с сохранением типов |
| `first_dns` | `{{ test["dns.servers"][0] }}` | Элемент массива в поле с точкой в имени |

Ссылки работают в таблице, JSON и YAML, в том числе внутри объектов и массивов.
В JSON/YAML записывайте их строками: `port: "{{ test.port }}"`. Если значение целиком состоит
из ссылки, тип источника сохраняется: число, bool, объект, массив или null. В составной строке
сложные значения сериализуются в JSON. ENV всегда строковая: объекты и другие нестроковые
значения передаются как JSON; отдельные поля для такого сопоставления автоматически не создаются.
Для автоматической передачи всего набора и `ИМЯ_ПОЛЕ` используйте вкладку **Ключи**.

Обычный текст `test.password` остаётся текстом. Обрабатываются только префиксы, объявленные
в этой группе; остальные выражения Ansible остаются нетронутыми. Содержимое прочитанного
секрета повторно как выражение не выполняется. Операторы, фильтры и вызовы функций не поддерживаются.

Сохранение не читает и не изменяет Vault: в БД остаются источники и выражения.
Обычные секреты без ссылок хранятся локально в зашифрованном виде. При каждом запуске
TaskExec читает актуальные значения и передаёт их через механизм секретов задачи.
Ошибка чтения или исчезнувшее поле останавливают подготовку. Удалить используемый ключ нельзя;
удалить или переименовать префикс можно после исправления использующих его выражений.

## API

`/api/project/{project_id}/secret_storages` поддерживает GET/POST, путь с `/{storage_id}` —
GET/PUT/DELETE. При PUT передайте совпадающие `id` и `project_id`.
Параметры подключения: `params.url`, `params.mount`, `params.namespace`, `params.kv_version`.
Поле `secret` принимает токен при записи; GET может вернуть имя файла или переменной окружения
вместе с `source_storage_type`. Ответы создания и изменения не повторяют токен.

Описание протокола: [Vault KV v1](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v1),
[Vault KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2).

### Расширенные реквизиты API

`params` содержит `auth_method` (`token`, `approle`, `kubernetes`, `jwt`, `cert`), `auth_mount`,
`auth_role` и флаг `without_secret_id` только для AppRole. Объект `credentials` содержит поля
`token`, `role_id`, `secret_id`, `jwt`, `client_cert`, `client_key` и необязательное `ca_cert`.
Каждое поле имеет вид `{ "source": "database|env|file", "value": "..." }`.
Допускаются только поля выбранного способа входа. GET возвращает признак `configured` и скрывает
значения из БД; ссылки на файл и окружение остаются доступными для редактирования.
`clear: true` явно удаляет необязательный реквизит. В публичных `params` секретов нет.
Подключение и реквизиты обновляются одной транзакцией.

POST `/api/project/{project_id}/secret_storages/test` принимает такой же черновик. При проверке
существующего подключения передайте его `id`, чтобы использовать сохранённые реквизиты.
Для проверки требуется право управления ресурсами проекта.

Тип подключения — `vault`; способ входа по умолчанию — `token`.
Ответы создания и изменения не возвращают переданные значения реквизитов.

### Редактирование ссылок через API

POST/PUT `/api/project/{project_id}/keys[/<key_id>]` с `reference_only: true` сохраняет
ссылку без запросов чтения или записи в Vault. Передайте `type` (`object`, `string`, `ssh` или
`login_password`), `source_storage_type: "vault"`, `source_storage_id`, `source_storage_key`
(только путь) и `source_mapping`: для строки `{"value":"dns_server"}`, для логина/пароля
`{"login":"user","password":"pwd"}`, для SSH `{"private_key":"pem","login":"user","passphrase":"phrase"}`.
Для `object` сопоставления пустые. Необязательные сопоставления можно опустить.
Для PUT нужны совпадающие `id` и `project_id`; `override_secret` и `generate_ssh_key` должны
быть `false`, а поля значений секретов — пустыми. Для ссылки обязательны хранилище и путь.
Ограничения типов ключей, используемых в настройках доступа к хостам, продолжают действовать.
DELETE того же ресурса с `?reference_only=true` удаляет только ссылку. Эти режимы использует
интерфейс; режим API для записи описан выше.

### Поля, предпросмотр и привязки API

Поле **Путь к секрету** загружает первый уровень хранилища. Выберите каталог с `/`
или начните вводить путь: после `/` загружается содержимое этого каталога, а введённая
часть имени фильтрует список. Для подсказок нужны права Vault `list` на каталоги:
`secret/metadata/...` для KV v2, `secret/...` для KV v1. Если `list` запрещён,
путь можно ввести вручную; доступ `read` проверяется отдельно при загрузке полей.

- POST `/api/project/{project_id}/secret_storages/{storage_id}/paths` с `{"path":""}`
  возвращает первый уровень: `{"paths":["apps/","proxmox"]}`. Для каталога передайте
  `{"path":"apps/"}` — ответ содержит полные относительные пути, например `apps/db`.
  Рекурсивного обхода и чтения значений нет. Отсутствующий каталог возвращает пустой список.
- POST `/api/project/{project_id}/secret_storages/{storage_id}/fields` с `{"path":"proxmox"}`
  возвращает `fields: [{"name":"dns_server","type":"string"}, ...]` без значений.
- POST `/api/project/{project_id}/keys/{key_id}/preview` возвращает `value`, `type` и `read_at`.
  Это явное чтение актуального значения строки/набора; SSH, пароли и служебные ключи запрещены.
- POST `/api/project/{project_id}/keys/{key_id}/fields` возвращает только пути полей:
  `{"paths":["",".username",".password"]}`. Пустой путь означает весь ключ.
- Все эти методы требуют управления ресурсами проекта и возвращают `Cache-Control: no-store`.
- POST/PUT группы переменных принимает `key_bindings`, например
  `[{"key_id":12,"name":"blabla","type":"var","field":null}]`.
  `type` — `var` или `env`; `field: null` — всё значение, `field: "dns_server"` — поле набора.
  Обычный GET группы возвращает ссылки без разрешённых значений. Резервные копии проекта
  сохраняют привязки по именам ключей и восстанавливают их с новыми ID.
- Для выражений POST/PUT группы принимает `key_sources`, например
  `[{"key_id":12,"prefix":"test"}]`. В `json` и `env` ссылки остаются строками:
  `{"dns":"{{ test.dns_server }}"}`. Выражения вкладки «Секреты» передаются отдельно:
  `"secret_expressions":[{"name":"PASSWORD","type":"env","expression":"{{ test.password }}"}]`.
  Источники также сохраняются в резервных копиях по именам ключей и восстанавливаются с новыми ID.
